# Identity and Representation

This document defines the domain distinction among native identity, semantic identity, and concrete representations.

## 1. Identity layers

Project Knowledge recognizes at least three materially different identity layers.

### 1.1 Source System identity

Identifies the native system in which an object exists.

Examples:

- Git repository `monad-framework/monad`;
- GitHub Issues for one repository;
- Wiki.js instance;
- CI provider/project;
- external standards corpus.

### 1.2 Native object/state identity

Identifies an object using the native system's own semantics.

Examples:

- Git commit SHA;
- GitHub issue number plus repository identity;
- ADR stable identifier;
- wiki page ID;
- workflow run ID.

A native identity may itself contain both mutable and immutable pieces.

### 1.3 Project Knowledge Subject identity

Identifies a logical engineering Subject whose continuity must survive changes in representation, location, or native tool.

Subject identity is optional and exists **in addition to** native identity.

## 2. Native Reference

A Native Reference is the inspectable bridge to a native source.

Conceptually:

```text
NativeReference
├── source_system
├── native_object_id?          # stable if the source has one
├── locator?                   # path, URL, ref, etc.
├── source_state_id?           # commit/version/revision when relevant
└── fragment?                  # section, line range, field, subresource
```

The implementation representation remains open.

### Invariant: locator != immutable state identity

The model MUST preserve distinctions such as:

```text
branch: main            mutable symbolic locator
commit: abc123          immutable Git source-state identity

path: docs/ADR-1.md     mutable storage locator
ADR-0001                stable domain/native decision identity
```

## 3. Subject

A Subject is introduced only when semantic continuity has demonstrated value.

### 3.1 Subject identity rule

Within a Project:

```text
Subject ID → one logical Subject
```

The identifier MUST NOT be reused for a different logical Subject.

### 3.2 Subject continuity

A Subject MAY survive:

- file rename;
- directory move;
- migration between tools;
- regeneration of a projection;
- change of current implementation;
- addition/removal of Representations.

Continuity does not mean all revisions are equivalent in content or authority.

### 3.3 Subject creation threshold

A Subject SHOULD be introduced when one or more of these is true:

- multiple native representations need to be treated as concerning the same logical thing;
- identity must survive relocation or tool migration;
- cross-tool relationships need a durable endpoint;
- authority/evidence must be attached independently of a storage locator;
- a user must ask “show me everything concerning this thing” across tools.

A Subject SHOULD NOT be created solely because an artifact was indexed.

## 4. Representation

A Representation participates in project memory by referring to a concrete native object or fragment.

Conceptually:

```text
Representation
├── native_reference
├── subject?                 # semantic binding when needed
├── role(s)?
├── provenance?
├── temporal qualifiers?
└── context qualifiers?
```

### 4.1 Cardinality

A Subject:

```text
Subject 1 ───── 0..* Representation
```

A native artifact MAY concern several Subjects. The implementation therefore MUST NOT assume one physical file equals one Subject.

A Subject MAY have no current Representation if, for example, it is a planned concept or a historical Subject whose artifacts are unavailable but whose identity is retained.

### 4.2 Representation role is not authority

A role describes **how a Representation participates**.

Authority describes **what it governs**.

For example:

```text
Representation role: generated projection
Authority: none beyond its derivation lineage

Representation role: ADR document
Authority: architecture decision concern, if policy grants it
```

The model MUST NOT infer authority merely from role labels.

## 5. Bindings and equivalence

A semantic binding states that a Representation concerns a Subject.

A binding may be:

- explicitly authored;
- imported from a stable native identifier;
- deterministically generated by project policy; or
- inferred/suggested.

The origin MUST remain inspectable when trust depends on it.

### 5.1 False-merge safety

Two artifacts that look similar MUST NOT automatically become one Subject solely because they:

- share a title;
- share text;
- have similar embeddings;
- have nearby paths;
- link to the same issue;
- were changed in the same commit.

Semantic equivalence requires stronger evidence or explicit policy.

### 5.2 Split and merge are not ordinary rename

If one logical Subject becomes two, or several become one, the original identity MUST NOT simply be reassigned.

The domain should preserve distinct Subjects plus explicit relationships describing the transition when the project chooses to model it.

A universal split/merge vocabulary is deferred.

## 6. Representation families

The domain does not freeze one universal role taxonomy, but it recognizes several recurring distinctions because requirements depend on them.

### Source representation

An authored/native source artifact.

### Projection

A representation derived to show selected information for another system or user job.

### Generated derivative

Machine-generated output derived from one or more inputs.

### Implementation representation

Source code, configuration, or another implementation artifact concerning a Subject.

### Evidence representation

An artifact used as evidence input or containing an evaluation result.

### Coordination representation

A work/communication surface whose state may mirror or coordinate around a canonical source elsewhere.

### Historical representation

A retained representation primarily useful for historical reconstruction rather than current operation.

### External representation

A source outside the project's directly managed systems, such as a standard or vendor document.

### Narrative representation

An authored explanation or learning view that cites project-memory sources but is not automatically authoritative for their underlying claims.

## 7. Identity resolution outcomes

When Project Knowledge attempts to connect native artifacts, valid outcomes include:

- `same-subject` — sufficient evidence/policy establishes one Subject;
- `different-subjects` — evidence establishes distinct Subjects;
- `related` — artifacts are related but not semantically identical;
- `unknown` — identity relationship is unresolved.

`unknown` is a first-class safe result.

## 8. Derived queries

The model should eventually support questions such as:

```text
Given native artifact A:
  Does it have a Subject?
  Which Representations concern that Subject?
  Which are current, historical, generated, or external?
  Which relationships are explicit vs inferred?

Given Subject S:
  Which native systems represent it?
  Which source-state revisions are known?
  Did its storage location change?
  Which authority assignments apply?
```
