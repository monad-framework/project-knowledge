# Inception

This directory defines why Project Knowledge should exist before the project commits to how it should be built.

The inception phase should answer five questions:

1. What problem are we actually solving?
2. For whom is that problem significant?
3. What outcomes would make the project useful?
4. What principles should constrain future design choices?
5. What are we deliberately not assuming yet?

## Documents

- [`problem.md`](problem.md) — the problem as currently understood.
- [`vision.md`](vision.md) — the desired future state if the project succeeds.
- [`principles.md`](principles.md) — design principles that should guide discovery and architecture.
- [`goals-and-non-goals.md`](goals-and-non-goals.md) — current scope boundaries.
- [`terminology.md`](terminology.md) — provisional language used during inception.

## Inception rule

Documents in this directory may contain hypotheses, but hypotheses must be labeled as such. Inception should not silently turn preferred implementation ideas into requirements.

## Exit criteria

Inception is complete enough to enter discovery when:

- the problem can be explained without referring to a proposed technology;
- goals and non-goals are explicit;
- major terms are understandable;
- the initial principles are internally consistent; and
- we can collect representative real-world engineering information to test the problem statement against.
