# PKC-0005 — Verification evidence invalidates itself through lifecycle persistence

## Source context

Project: Monad

Source:

- GitHub issue `#180` — `[Defect] EOSV evidence freshness self-invalidates across VERIFYING transition / machine projection sync`
- https://github.com/monad-framework/monad/issues/180

Observed during `WP-MVP-0001` verification.

## Observed situation

EOSV generated validation evidence successfully, but subsequent lifecycle and projection persistence caused the freshly generated evidence to be considered stale.

The evidence fingerprint included mutable control-plane state and the current Git `HEAD`. Normal verification changed lifecycle status, synchronized machine projections, and required commits that changed `HEAD`. As a result, the act of persisting the verification process altered the fingerprint used to decide whether the evidence was still fresh.

A successful verification therefore lacked a stable committed fixed point even though the relevant product source had not changed.

## Information involved

- evidence records;

- Git commit identity;
- semantic product source; and
- freshness status.

## Why this is difficult to organize

The case exposes several different notions of change that a simple version history does not distinguish automatically:

- semantic change to the thing being verified;
- control-state change caused by verification;
- derived projection change;
- evidence persistence change;
- commit identity change.

Treating all of these as equivalent source drift makes evidence unusable. Ignoring all of them would make evidence unable to detect real drift.

The useful project knowledge is not merely `this evidence exists`; it includes exactly what semantic state the evidence supports and what changes should invalidate that support.

## Candidate relationships

- evidence `supports` verified assertion;
- evidence `produced by` validator;
- evidence `evaluates` source state;
- evidence `has freshness relation to` source state;
- lifecycle transition `causes` control-state mutation;
- projection `derived from` canonical control state;
- commit `contains` persistence-only changes;
- semantic source change `invalidates` evidence.

## Time, authority, provenance, and context

### Time

Evidence has a capture time and later audit times. Freshness is a relation between those moments and relevant source state.

### Authority

The evidence is authoritative only for the state and claims it actually verified. A generic repository commit identity is broader than that semantic authority.

### Provenance

Useful provenance requires more than the validator name and commit SHA; it must identify the meaningful verification inputs.

### Context

Control-plane mutation generated by the verification workflow should be understood differently from independent product drift.

## Recovery questions

- What exact state did `EVID-0001` verify?
- Which later changes were merely consequences of verification?
- Did any semantically relevant product input change?
- Why was the evidence marked stale?
- What kinds of change are intended to invalidate this evidence?
- Can the verified source state be reconstructed independently of incidental control commits?

## Provisional observations

1. Evidence validity is a semantic relationship, not merely equality with a repository-wide version identifier.
2. Different classes of change can have different relevance to an assertion or evidence record.
3. Provenance needs enough granularity to identify what was actually observed or verified.
4. A project-memory system that tracks temporal validity may need to distinguish semantic state changes from incidental persistence changes.
5. Verification artifacts can participate in causal loops with the state they describe.

## Open questions

- How should relevant-versus-incidental change be determined without introducing brittle hand-maintained exclusions?
- Can evidence scope be derived from declared dependencies or must it be recorded at capture time?
- How should the system represent that an artifact is current for one claim but stale for another?
