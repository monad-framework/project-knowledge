# Acceptance Principles

These principles define how later domain, architecture, and implementation work must demonstrate that the requirements are actually satisfied.

They are not yet executable acceptance tests. They are the rules from which those tests must be derived.

## AP-001 — Test the user-recovery outcome, not only data presence

A requirement is not satisfied merely because metadata fields exist.

Acceptance scenarios must demonstrate the user job the metadata is intended to support.

Example:

```text
insufficient:
  artifact has authority_scope field

required direction:
  given conflicting representations,
  a user can determine which source governs the disputed property
  and inspect why
```

## AP-002 — Include negative and ambiguity cases

Semantic requirements must be tested against cases where the answer is intentionally **unknown**, **historical**, **stale**, **conflicting**, or **unresolved**.

The system must demonstrate that it does not manufacture certainty merely because a query expects one answer.

## AP-003 — Verify native-source fidelity

Integration acceptance must prove that:

- native identifiers remain recoverable;
- native source meaning is not silently changed;
- native authority boundaries remain visible; and
- Project Knowledge can be disabled or unavailable without destroying ordinary access to native artifacts where graceful degradation is required.

## AP-004 — Verify semantic identity across relocation

At least one acceptance scenario must demonstrate a semantic subject whose native representation is moved or renamed while its logical identity remains continuous.

A separate scenario must demonstrate that two superficially similar artifacts are **not** merged into one semantic identity without sufficient basis.

## AP-005 — Verify representation-role distinctions

Acceptance scenarios must demonstrate at least one source/projection relationship in which:

- a generated or coordination representation is linked to its source;
- the projection can become stale;
- the projection does not gain independent corroborating authority; and
- a user can inspect the lineage.

## AP-006 — Verify scoped authority

Authority tests must include:

1. an artifact authoritative for one property but not another;
2. two representations with different legitimate authority scopes; and
3. a case in which authority cannot be resolved and the system preserves the unresolved state.

## AP-007 — Verify current-versus-historical clarity

Acceptance must include a case in which an earlier statement remains historically valid but is no longer current.

The current view and historical view must both be recoverable without presenting the historical statement as current instruction.

## AP-008 — Verify valid-time versus recorded-time behavior conditionally

Where explicit dual-time semantics are implemented, tests must include a retrospective correction in which:

```text
valid/effective time != recorded/system time
```

The system must reconstruct both what was believed/recorded at an earlier point and what the corrected understanding says was actually valid.

A simple project that does not enable explicit dual-time semantics must also remain conforming where Git/native history is sufficient.

## AP-009 — Verify provenance semantics, not only links

Provenance tests must distinguish materially different relations such as:

- generated by;
- derived from;
- used input;
- attributed to;
- revision of; and
- observed in a particular context,

where those distinctions are present in the implemented domain model.

The exact vocabulary may differ, but collapsing all of them into one untyped `source` field must fail conformance for complex cases.

## AP-010 — Verify reconstruction without ephemeral host dependence

Historical reconstruction tests must demonstrate that deletion or absence of a temporary worktree, local path, host directory, or other ephemeral execution location does not change the interpretation of retained canonical historical state when that state claims to be reconstructable.

## AP-011 — Verify claim-relative evidence

Evidence acceptance must include:

1. evidence tied to an explicit proposition;
2. the exact source state and method used;
3. an unrelated change that must **not** invalidate the evidence when relevance is known; and
4. a relevant change that **must** invalidate or question the evidence.

A separate case must demonstrate that a passing validator cannot be presented as proving a stronger proposition than it actually checked.

## AP-012 — Verify correction without erasure

A correction scenario must preserve:

- the prior retained statement;
- the corrected current statement;
- temporal/status distinction;
- the correction relationship; and
- supporting provenance/evidence where available.

## AP-013 — Verify contradiction diagnosis without false reconciliation

Contradiction diagnostics must be exercised against multiple disagreement causes, including at least:

- stale projection;
- historical difference;
- context difference;
- authority difference; and
- unresolved disagreement.

The system must not classify a contradiction when the available evidence is insufficient.

## AP-014 — Verify relationship impact with provenance

Impact analysis must distinguish:

- explicitly recorded dependency/relationship;
- derived relationship with known rule; and
- speculative or suggested relationship,

where the implementation supports all three.

Impact output must not imply certainty beyond relationship provenance.

## AP-015 — Verify retrieval does not become truth arbitration

Retrieval tests must demonstrate that a highly ranked stale, generated, or non-authoritative result does not become current truth merely because it ranks above the authoritative source.

Exact identifier lookup and semantic/content retrieval should coexist where implemented.

## AP-016 — Verify progressive formalization

Conformance must be tested at more than one project complexity level.

At minimum:

### Minimal project

A project using ordinary files, native IDs, Git/history, links, and search should obtain useful Project Knowledge behavior without being forced to define the full semantic model.

### Enriched project

A project with multiple representations, scoped authority, provenance, temporal distinctions, and evidence should be able to add those semantics incrementally.

A design that works only after full migration to a highly structured model fails this principle.

## AP-017 — Verify graceful degradation

Where the architecture uses generated indexes, projections, caches, search services, or derived databases, later acceptance tests must demonstrate what remains available when each derived component is unavailable or rebuilt.

Canonical/native project knowledge must not disappear solely because a derived convenience layer is lost.

## AP-018 — Verify access-boundary preservation

Later security acceptance tests must prove that indexing or federation does not expose a source artifact to a principal who lacks the required source/project authorization.

The exact authorization architecture remains open, but this behavior is mandatory.

## AP-019 — Prefer corpus-derived fixtures

Where practical, formal acceptance fixtures should be derived from the real `PKC-*` corpus rather than only from synthetic happy paths.

At minimum, the architecture/MVP acceptance plan should retain representative fixtures for:

- multi-view object identity;
- projection drift;
- worktree/context visibility;
- incidental source classification;
- evidence self-invalidation;
- provenance baseline mismatch;
- host-dependent historical state;
- summary drift;
- knowledge refinement; and
- semantic identity across relocation.

## AP-020 — Requirement-to-test traceability

Every normative `FR-*`, `QA-*`, and `CON-*` selected for an implementation milestone must trace to one or more:

- domain invariants;
- architecture decisions;
- specifications/interfaces; and
- executable acceptance or conformance tests.

A requirement may be intentionally deferred from an MVP, but it must not disappear silently.

## Readiness for domain modeling

The requirements set is ready to seed domain modeling when review confirms:

1. no requirement accidentally selects implementation technology;
2. requirements are behaviorally distinct enough to test;
3. scoped/optional behavior is not being interpreted universally;
4. non-requirements correctly protect the discovery hold boundary;
5. all functional requirements have capability/evidence trace; and
6. known evidence gaps remain visible.
